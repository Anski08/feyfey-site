How it's built

A local-first study app with a very small server.

FeyFey holds as little of your data as it can get away with. This page explains the storage split, the scheduling arithmetic, and why each boundary sits where it does.

Who builds it

One developer, building in the open.

FeyFey is an independent project. It is deliberately small: no framework, no build step, no analytics, and no tracking of any kind. The entire client is a single HTML document that talks to three serverless functions. That constraint is a feature — it keeps the attack surface, the hosting cost and the number of things that can silently break all close to zero.

About the name

The preview build still shows the earlier working name, Recall, in its interface and in some internal storage keys. FeyFey is the name going forward; the rename has not shipped yet. If you open the preview and see "Recall", that is why — not a different product.

The stack

Four moving parts.

LayerWhat it isWhat it holds
ClientOne static HTML file, vanilla JavaScript, no framework or bundlerEverything, while you use it
Browser storageIndexedDB for video files, localStorage for the working copy of your libraryYour video files — permanently and exclusively
DatabaseHosted Postgres with row-level security and email authenticationYour account, your schedule metadata, your subscription status
FunctionsThree serverless endpoints for billing onlyNothing persistent

There is no media server, no object storage bucket, and no content delivery network holding user files. That is not an omission — it is the central design decision, and everything else follows from it.

Storage model

Heavy data stays put. Light data travels.

Every item in your library is split in two. The video file — tens or hundreds of megabytes — is written to IndexedDB under a generated identifier and never leaves the browser that received it. Playback uses an in-memory object URL, so even rendering the video involves no network request.

The description of that item is a few hundred bytes: a title, a subject, a priority, an optional question, a list of bookmark labels with their timestamps, and the scheduling state. That is what is written to the database, debounced so that rapid edits collapse into a single write.

The consequence is the one we state plainly on the overview page: sign in on a second device and your library appears with its full schedule intact, but each video shows as missing until you attach the file on that device too.

The scheduler

An SM-2 variant, stated in full.

Each item carries two numbers: an interval in days, starting at zero, and an ease factor, starting at 2.5. Every rating transforms both. Nothing else is consulted — no hidden model, no server-side scoring.

RatingNew intervalEase factor
Forgot 1 day reduced by 0.2
Hard first review 1 day, then interval × 1.2 reduced by 0.1
Good first review 3 days, then interval × ease unchanged
Easy first review 4 days, then interval × ease × 1.3 increased by 0.1

Intervals are rounded to whole days and the next review date is stored as a plain calendar date, so a review is due on a day rather than at an hour. The ease factor is clamped at a floor of 1.3; without that floor, an item you repeatedly fail would collapse toward a permanent one-day loop and crowd out everything else.

Why the intervals are shown on the buttons

Each rating button displays the interval it will produce before you press it. Spacing algorithms usually hide this, which trains people to distrust them. Showing the consequence makes the rating an informed choice and makes the system auditable by the person using it.

Why Easy carries an extra multiplier

Plain SM-2 treats a confident answer and a correct-but-effortful answer almost identically. The additional 1.3 factor on Easy pushes genuinely known material out of the queue faster, which matters when each item is a video that costs minutes rather than a card that costs seconds.

The daily queue

Ordered by urgency, then capped.

Overdue

Anything whose next review date has already passed. These come first, because a missed review is the point at which a spacing schedule starts to decay.

Due today

Items scheduled for exactly today.

New, by priority then age

Videos you have added but never reviewed, sorted high priority first, and oldest first within a priority. New material is last so that adding a batch of videos never buries the reviews you already owe.

The combined list is then truncated to your daily goal — 4, 8, 12 or 20 videos. The cap exists so the session has a definite end. An unbounded queue is the fastest way to make someone stop opening an app.

Security model

The database refuses to serve other people's rows.

The client holds a publishable API key, which is normal for this architecture and safe by design: every table enforces row-level security, so the database itself checks the identity attached to each request and will only return rows belonging to that account. The key grants the ability to ask, not the ability to read.

What you can write

Your own study data — your library, bookmarks and schedule. Reads and writes are both constrained to rows carrying your own account identifier.

What you cannot write

Your subscription status. That table is readable by you and writable only by the server, which updates it in response to signed events from the payment processor. A client cannot grant itself access.

Payment card details are never seen by FeyFey. Checkout and billing management are handled on the payment processor's own hosted pages, and the server receives only signed notifications about subscription state.

Trade-offs

What this design costs.

No cross-device files

The direct price of never uploading. A future fix is peer-to-peer transfer between your own devices, which keeps the property intact; server-side storage would not.

No backup

Clearing browser data destroys the files, and we cannot restore them because we never had them. Export tooling is the most important missing feature.

Browser storage limits

Large libraries can bump into per-site storage quotas, and some mobile browsers reclaim storage aggressively under pressure.

These are consequences of the storage decision, not bugs. We would rather name them here than let someone discover them after they have built a library.
